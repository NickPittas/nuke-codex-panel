# Research: static type checking for Nuke Python (advice only)

Researched 2026-10-29. Nothing was installed, run or changed in this repo. Statements marked **[INFERENCE]** were not observed in a run.

## Bottom line

1. **No evidence of a stub set verified for Nuke 17.1.** Foundry's 17.1 docs describe the API but I found no official `.pyi`/type-stub distribution. The two community projects are generated from older Nuke builds (13 and 15) by introspecting the interpreter. Do not claim 17.1 support from either.
2. **If we use static checking at all, start with advisory batch checks (Pyright CLI, `--outputjson`) on the model's code.** Batch is the simplest first option, not an inherently more accurate one: Pyright is one type engine delivered as both a CLI and a language server ([features](https://raw.githubusercontent.com/microsoft/pyright/main/docs/features.md)), so a full LSP would give the same diagnostics. Do not make every diagnostic blocking. Inaccurate or incomplete stubs, dynamic Nuke APIs and session-persisted bindings all produce false errors. Block only on diagnostics backed by a verified contract (for example a member confirmed absent in a stub regenerated from the live install).
3. **With the current generic community stubs, static checking covers only a thin slice of the failures we have seen.** It can catch missing module members, bad arity and `Optional` misuse when the stub is accurate. It cannot see knob names, `nuke.nodes.<Class>` kwargs, which node classes exist or which plugins are loaded, because those stubs type them generically. Stubs generated per Nuke version and plugin set, with overloads or schemas per node class and knob, could improve that coverage; that is untested here. Live-installation data is the runtime authority for those facts. The existing docs search-then-read gate only tracks that the model searched and read a document; it is not a runtime authority or a correctness proof, and the attribution gaps noted in repo memory remain.
4. **Stubs are only as good as the docs they were generated from.** Bad or ambiguous docstrings become wrong signatures, so a type checker can produce false errors and false passes.

## Evidence

### Official Foundry API (17.1)
- The reference is Sphinx autosummary of runtime docstrings, not typed signatures. Example: `nuke.createNode` is listed as `createNode(node, knobs, inpanel) -> Node` ([nuke module](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/_autosummary/nuke.html)). `nuke.Nodes` is documented as an empty class with no methods ([nuke.nodes](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/_autosummary/nuke.nodes.html)).
- Submodules are documented as `nuke.curvelib`, `nuke.curveknob`, `nuke.rotopaint`, `nuke.splinewarp`, `nuke.gsv`, etc. ([guide index](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/)). The `nuke.rotopaint` page says "Use help('_rotopaint') to get detailed help" ([page](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/_autosummary/nuke.rotopaint.html)). The native names carry an underscore, so docs and runtime names differ. `nuke.rotopaint` and `nuke.curvelib` each list their own `AnimCurve`, `AnimControlPoint`, etc. Which native module a real object belongs to is a runtime question.
- Guide examples still use Python 2 syntax (`print shape.name`, `raise TypeError, '...'`) on the [Roto and RotoPaint page](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/rotopaint.html). Doc snippets are not safe to feed to a Python 3 parser, and doc-derived stubs inherit that noise.
- Official dynamic-creation idiom: `nuke.nodes.nodename(control=value)` with named args that set knobs ([basics](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/basics.html)). Foundry warns that `nuke.nodes.<name>` on a plugin file that is not a node may crash Nuke. Knob access is `node['size']`, and knobs can be added at runtime with `addKnob`.
- Nuke can be imported as a Python module with the interpreter Nuke ships; other interpreters "should work" but only the bundled one is supported ([Nuke as a Python Module](https://learn.foundry.com/nuke/developers/17.1/pythondevguide/nuke_as_python_module.html)). That is the supported way to introspect the real 17.1 API headlessly.

Pyright says generated stub drafts "typically" need cleanup and omit things it cannot infer ([Type Stub Files](https://raw.githubusercontent.com/microsoft/pyright/main/docs/type-stubs.md)).

### What the existing stubs show about dynamic APIs (read from cg-stubs `_nuke.pyi`, Nuke 13 era)
- `Nodes.__getattr__(self, item) -> NodeConstructor[Node]` and `NodeConstructor.__call__(self, *args, **kwargs) -> NodeT`. So `nuke.nodes.Anything(any_kwarg=...)` type-checks as a `Node` with no knob or class validation. A few well-known classes (`Group`, `BackdropNode`) are declared explicitly.
- `Node.__getitem__(self, name: str) -> Knob` and `Node.knob(...) -> Optional[Knob]`. The returned `Knob` is not the concrete subclass, so a typo in the knob name is not caught, and `setValue` arguments are not checked per knob type. Real failures show up only at runtime (the repo's own note: `Node['missing_knob']` raises `NameError` through a C slot).
- `toNode(s) -> Optional[Node]`: a checker can flag unchecked `.knob` access on `None` (Pyright rule [`reportOptionalMemberAccess`](https://raw.githubusercontent.com/microsoft/pyright/main/docs/configuration.md), default `error`). That is a genuine win.
- Roto: `_curveknob.pyi` defines `Layer` (with `append`), `Shape`, and `ShapeControlPoint` with `center`, `leftTangent`, `rightTangent`, `featherLeftTangent`, `featherRightTangent` as `AnimControlPoint`. `_curvelib.pyi` defines `AnimCurve` with `getNumberOfKeys()`/`getKey(index)`, `AnimCurveKey`, and `getSkewXAnimCurve`. My grep of `_curveknob.pyi` found no `addItem` and no `AnimControlPoint` class definition there. **[INFERENCE]** Those two members would therefore have been flagged as missing, which matches the two native AttributeErrors recorded in repo memory. I did not run it.
- `rotopaint.pyi` is a ~422-byte re-export of `curveknob` plus four `convertTo...` functions. Whether it matches 17.1's `nuke.rotopaint` (which the 17.1 docs show with many more classes) is unverified.

### Pyright / Pylance behavior
- Resolution order: `stubPath` (default `./typings`), then workspace code, then installed stub packages (`*-stubs`) / inline stubs / `py.typed`, then typeshed ([import resolution](https://raw.githubusercontent.com/microsoft/pyright/main/docs/import-resolution.md)). A `typings/nuke/` directory therefore wins over everything and needs no install. For packages without a stub or `py.typed`, symbols are `Unknown` ([type stubs](https://raw.githubusercontent.com/microsoft/pyright/main/docs/type-stubs.md)).
- Pylance honors `python.analysis.stubPath` (single directory) and partial stub packages (`*-stubs` with `py.typed` containing `partial`) ([Pylance stubPath](https://raw.githubusercontent.com/microsoft/pylance-release/main/docs/settings/python_analysis_stubPath.md)). It is the same engine ("powered by the Pyright static type checker").
- CLI: `pyright --outputjson [files]`, `-p`, `--pythonversion`, exit code 1 on errors, diagnostics carry `rule`, `severity`, zero-based `range` ([command line](https://raw.githubusercontent.com/microsoft/pyright/main/docs/command-line.md)). Ships as both CLI and language server ([features](https://raw.githubusercontent.com/microsoft/pyright/main/docs/features.md)).
- Relevant rules and defaults ([configuration](https://raw.githubusercontent.com/microsoft/pyright/main/docs/configuration.md)): `reportAttributeAccessIssue`, `reportCallIssue`, `reportArgumentType`, `reportUndefinedVariable` are `error`; `reportMissingModuleSource` is `warning` (stub found, runtime module not found, expected when `nuke` is not importable in the checker's environment); `reportIncompleteStub` (module-level `__getattr__` in a stub) is `none`.
- Typing guidance: a stub with a module-level `__getattr__` marks an incomplete stub, and `__getattr__` on a class means any attribute is accepted. Both silence real errors ([writing stubs](https://raw.githubusercontent.com/python/typing/main/docs/guides/writing_stubs.rst)). A partial stub is useful for coverage but weakens negative results.
- Pyright's own docs say libraries that replace the loader, thin native shims, or heavily dynamic behavior are poor static targets ([type stubs](https://raw.githubusercontent.com/microsoft/pyright/main/docs/type-stubs.md)).

## What static checking can and cannot do for us

| Question | Static (Pyright + stubs) | Where the answer really lives |
|---|---|---|
| `nuke.<function>` exists, argument count/kind | Yes if stub is accurate for 17.1 | Runtime-verified inventory of the live 17.1 `nuke` namespace |
| `Node.method` exists on the returned type | Partly; `nuke.nodes.X()` is `Node`, not the node class | Runtime class of the actual object |
| `nuke.nodes.Foo` class exists, which kwargs/knobs it has | Not with the current generic stubs (`__getattr__` accepts everything). Per-class stubs generated from the live install might. | Runtime-verified registry/inventory of node classes in the user's session, node docs, a live node's knobs |
| `node['knob']` exists / value type is right | Not with the current generic stubs (returns generic `Knob`). Generated per-class overloads or schemas might cover part of it. | Live node; knobs vary per class, user knobs, plugins, version |
| `Optional` results (`toNode`, `knob`) dereferenced unchecked | Yes | n/a |
| Roto `_curvelib`/`_curveknob`/`_rotopaint` members | Only as far as the stub matches 17.1 (native modules, documented under `nuke.*` names) | Runtime introspection of the native objects |
| Plugin/version variation (OFX, gizmos, 3rd-party, 17.x point releases) | Only if stubs are generated per installation | Runtime inventory in the user's Nuke |
| Names defined by earlier `execute_python` calls | Only if declared to the checker (see below) | Our session state |

## Integration considerations for this repo
- `execute_python`'s namespace persists between calls and already contains `nuke` (see `mcp_server/server.py` tool description). A per-call static check would report `reportUndefinedVariable` for any name defined in an earlier call. The checker needs a known session binding set (a generated prelude that declares those names, or checking only against `nuke`-API rules and disabling undefined-variable) or it will be noisy. This is a design issue, not just configuration.
- `nuke_action` takes ordinary JSON, not Python. It does not need a Python type checker; its validation belongs to the action schema and runtime.
- The existing runtime recovery (api_errors tracking, docs-search-then-read gate) is not proof that code is correct: the gate only tracks whether the model searched and read a document, and the attribution gaps recorded in repo memory for native Roto errors remain. Live-installation data is the runtime authority. A checker would be a pre-execution advisory *complement* for a subset (for example missing module members), not a replacement.
- No tool or gate change is required by this research. It is only advice on whether a type checker is worth adding.

## Recommendation: batch vs full LSP
- **Batch Pyright** (one process per snippet or per saved file, `--outputjson`, repo-owned `typings/` or `stubPath`) is the simplest first option. It is stateless and easy to bound. Cost is a Node.js dependency and per-call startup; Pyright has a `--watch` mode if latency matters ([command line](https://raw.githubusercontent.com/microsoft/pyright/main/docs/command-line.md)). Start advisory: report diagnostics to the model as hints. Promote a rule to blocking only when its contract is verified against the live install (stub regenerated from it, session bindings declared). Otherwise false errors from inaccurate stubs, dynamic APIs and persisted-namespace names will block valid code.
- **Full LSP** uses the same Pyright type engine, so it is not inherently more accurate. Its possible advantages are persistent, incremental analysis (no per-call startup) and hover/completion/signature data that could be consumed by the model. It adds process and state management. Consider it after batch if latency or model-facing hover/completion proves useful; this has not been evaluated here.
- **Stub source:** do not adopt `types-nuke 13.2.8.0` or sisoe24 15.0v1 stubs as authority for 17.1. If stubs are wanted, regenerate against the installed 17.1 from Nuke's own interpreter (the method both projects use, supported by Foundry's "Nuke as a Python Module"), then hand-review dynamic parts (`Nodes`, `Node.__getitem__`, native Roto modules) and expect cleanup per Pyright's guidance. Do not use the permissive `__getattr__` escape for modules you want errors from.
- **Expectation:** with the current generic stubs, the main model failures we recorded (wrong knob names, nonexistent node classes, wrong Roto native calls) are only partly detectable. Keep live-installation inventory and introspection as the source of truth; treat the docs gate as a search/read tracker only.
