## Workflow (every feature, no exceptions)

0. **Reuse gate (before step 1).** For each requirement that looks custom, name the upstream capability checked first: Pi 1.4.0 built-in/RPC, existing plugin code, then [RESEARCH-pi-extensions.md](RESEARCH-pi-extensions.md). Reuse it, else adapt it narrowly, else build small glue for the measured gap; record the outcome under the feature's Known limits. A researched candidate (all source-read, untested on Pi 1.4.0) is **evaluation**-only until accepted: pin, license, code, private-auth, cost and no-hidden-model-call source review comes first, then a user-authorized private evaluation install/load, and only the full feature live run (below) makes it **accepted** for production or the normal allowlist.
1. **Build the whole feature.** Complete code for every requirement. The user prohibits creating tests, test harnesses and fixtures.
2. **Live run.** Exercise the actual production panel, bridge and MCP in an owned Nuke scene. Use existing production entrypoints; do not create test scripts or run test suites.
3. **Whole-feature review.** Review the complete feature and live evidence. Collect all defects into one batch.
4. **Fix the batch**, then rerun the whole feature live rather than only the fixed lines.
5. Repeat 3–4 until the batch is closed. Record the observed evidence and update affected existing documentation.
6. **Stop at the user's approval checkpoint.** Advance only when the user approves the next stage.

Rules:
- Mocks, fake processes and per-patch check loops are not feature proof; live Nuke is.
- No model-provider turn or credential grant without the user's explicit authorization for that run. Ask once per feature, naming provider, model, and the scenario.
- Requirement not passed = feature not done. Partial proof never advances the order.
- Parallel source work and live exercise require the user's explicit approval and separate ownership; neither worker may restart or reconfigure the other's running session.
- No automatic model interruption, deadline, retry or finish-up nudge anywhere; steering is manual only.
- Other harnesses (Codex, Claude, OpenCode, OMP) and global desktop/Pi config stay untouched.
- Never read or copy global Pi `node_modules`, extensions, config, auth or sessions into the private runtime.
- Extensions load only by explicit private path from a curated set (project-owned, or pinned/licensed/reviewed third-party); no global/project auto-discovery, and none may bypass bridge gates, trust or leases or read global credentials.
- Research adds no scope: no new timers, automatic side conversations, model-control behaviour or feature list growth without the user's explicit direction.

## F2 Private accounts and model selection

Status: **implemented, NOT ACCEPTED** (authorized 2026-10-30) · Evidence: whole native rerun after the single repair batch, `/tmp/nuke-private-pi-f2-v0vdu8t2/batch-native.txt` 7/7, `batch-storage.txt` 4/4 (including both refresh and close paths), `batch-f1-preservation.txt` 19/19 (F1 preserved), plus `/tmp/nuke-private-pi-f2-v0vdu8t2/batch-controlled-metadata-error.txt` (native controlled credential-env metadata failure: the client constructor returns an actionable error and no helper process is started; Qt PNG visually inspected). Earlier first battery: `first-native.txt`, `first-storage.txt`, `first-f1-preservation.txt`, `native-summary.json`, `storage-summary.json`. The real SDK 1.4.0 catalog returned 41 API-key + 9 OAuth entries (50), all `canLogin`. These proofs use offline SDK fixtures (storage/history) with a nonfunctional fixture key in a separate agent dir, removed by SDK logout; they are NOT real authentication, no real credential, provider request, model turn or grant was used, and the RPC child was never started with a fake credential · Defect batch: whole-feature correctness (5) and security (7) review findings repaired as one batch; native rerun passed · Known limits: acceptance pending the human gate below; no provider shortlist.

**Implemented.**
- **Catalog:** the full dynamic SDK catalog, one entry per (provider, auth type), no hardcoded or preferred provider list. Ambient-only API entries (no Pi login) are shown as informational only; no flow is invented.
- **Where:** Settings dialog button "Pi accounts…" (`ui/settings_dialog.py`) opens `ui/accounts_dialog.py`; usable whichever harness is selected. Panel button wiring is in `ui/panel_widget.py`. Model choice stays the existing panel dropdown.
- **Flows:** the user first picks API key or Subscription/OAuth, then a provider. API key uses a masked secret prompt. OAuth shows the SDK's own interactions mid-flow: browser/headless/device select, auth URL, device code, manual callback/code, progress, per-prompt withdrawal and errors. Qt only opens HTTP(S) links when the human clicks "Open browser"; the SDK never opens a browser. Cancel sign-in aborts the whole login.
- **Storage:** private SDK store only (`<managed Pi dir>/auth.json`, `0600` in a `0700` dir, not encrypted). Credentials flow over helper stdin and the SDK store only: never argv, QSettings, chat, logs, traces or inherited/global environment. Global `~/.pi` and inherited provider environment are never borrowed. SDK-supported external-store choices (e.g. AWS profile, ADC) are used only if the user explicitly picks them; that choice relies on credentials outside the private store, so Check/logout cannot remove them and the UI warns.
- **Helper:** `runtime/pi/auth-helper.mjs` (public `ModelRuntime`, no session/extensions/settings, `allowModelNetwork:false`), driven by `harnesses/pi_auth.py` (`PiAuthClient`, JSONL over stdin/stdout).
- **Check** = local credential resolution through `getAuth`, plus OAuth renewal only if the SDK decides it is needed. It is NOT provider/API-key validation and NOT a forced refresh. The catalog never resolves or refreshes accounts (no network); `configured` is local presence/resolvability only (OAuth: token validity unchecked).
- **Refresh cannot be cancelled** (the SDK persists rotated tokens even after cancellation): Cancel is disabled, and closing the dialog/stopping the helper waits until the SDK has finished persisting, then honours the close. No new timer or retry.
- **Logout** removes the local credential only; no provider-side revocation. No-op logouts and checks do not renew the Pi process.
- **Propagation:** a persisted credential change (or unknown persisted outcome, including saved-with-sync-warning) emits `accounts_changed`; the managed Pi RPC client renews its idle process on the same session so the model list updates (empty lists are published authoritatively) without losing the chat. If busy, the change is held and coalesced; there is no automatic abort, timer or retry loop. Other harnesses are untouched.

**Outcome.** In the retained Qt UI the user can add an API key, log in with a supported subscription (browser/device/manual-code), see status, cancel, hit errors, refresh, and log out; then pick a model, all against the private auth store.

**Reuse / modify (as implemented).** Minimal SDK auth helper on the pinned Pi (`ModelRuntime.login/logout`, `AuthInteraction` prompt/notify, private `authPath`/`CredentialStore`); RPC has no auth commands, so this is not a second assistant engine or parallel conversation. Qt: `ui/accounts_dialog.py`, `ui/settings_dialog.py`, `ui/panel_widget.py`. Auth changes reach the running RPC process through the existing idle-process renewal, preserving the SAME session and model selection after account changes; if the client is busy the change is deferred and coalesced, with no automatic abort or timers. The public SDK runtime reload does NOT refresh an already-running RPC process's snapshot, and there is no public RPC auth/reload command nor `ctx.modelRuntime` in extensions, so renewal is the only supported route. Providers/methods come from the SDK dynamically; not every provider has a subscription. Permissions per `docs/ARCHITECTURE-pi-runtime.md`; storage is not encrypted; OS keyring is deferred.

**Non-goals.** Importing or borrowing global keys; promising provider-side revocation on logout; keyring framework; secrets in chat, logs, traces or model context.

**Live scenarios (human-in-the-loop, required).** (1) Enter an API key by secret prompt, select a model, confirm a turn is authorized by the user. (2) Complete a real subscription login through each method the chosen provider offers (browser and device/manual code where available), plus cancel mid-flow and a bad code. (3) Logout; verify local credential removal and that no ambient env key is used. (4) Auth change mid-chat; conversation preserved. (5) Grep artifacts/logs/chat store for secrets.

**Gate.** Requires, all user-authorized and human-performed: a successful RPC model turn using the private API key AND a successful RPC turn using the private subscription login, both in the same chat (auth change propagates without losing it); actual OAuth refresh success and refresh failure handled through supported SDK refresh paths with no ambient-env fallback; after logout the provider is no longer authenticated until re-login, with no ambient fallback; private credential provenance confirmed on the first authorized turn (effective prompt and source). **Still PENDING human:** none of these have been performed, so no coverage is claimed. Missing human, provider or refresh prerequisite = F2 stays implemented but NOT ACCEPTED, with the reason; never mark passed by simulation. The agent never grants or revokes permissions, copies global credentials, or builds a new test framework.
