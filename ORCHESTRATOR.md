# ORCHESTRATOR.md — Nuke Codex Panel

> **Current product (supersedes the multi-harness description below):** *Nuke Pi* (repo/package `nuke-codex-panel`, Python package `nuke_codex_panel`) is a Pi-only dockable Nuke panel. The only backend is the official pinned Pi 1.4.0 on a private official Node 26.12.0 under `runtime/pi/` plus the owned extensions (`nuke-runtime.ts`, `auth-helper.mjs`, `credential-env.json`); a customized distribution, not a fork. Install with `python3 install.py --target PATH --nuke-dir PATH [--no-register] [--check]` (Linux x64, Windows x64, macOS x64/arm64; native verification Linux only). See [README.md](README.md), [docs/INSTALLATION.md](docs/INSTALLATION.md), [docs/USAGE.md](docs/USAGE.md), [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Codex/Claude/OMP/opencode references below and in the dated decision log are HISTORICAL, not runtime contract.

Repo brief
- Foundry Nuke agent panel (`~/.nuke/nuke-codex-panel`): dockable PySide6 chat client for Codex / Claude Code / pi / OMP / opencode harnesses. Pure-python package (`nuke_codex_panel/`), Python 3.11 under Nuke 17.1; no build step; symlinked into `~/.nuke` and registered via `menu.py` → `panel.py` → `ui/panel_widget.py`.
- Runtime: harnesses are subprocesses speaking JSONL (codex app-server, `claude -p stream-json`, pi/omp `--mode rpc`, opencode serve+SSE). Nuke MCP sidecar (`harnesses/nuke_mcp.py` + `mcp_server/server.py`) exposes five live bridge tools (`nuke_action` / `nuke_workflow` / `execute_python` / `get_nuke_context` / `capture_nuke_screenshot`) through one application-owned Qt TCP bridge (`bridge/lifecycle.py` + `bridge/server.py`), plus three read-only knowledge tools (`search_compositing_knowledge` / `get_compositing_guidance` / `get_node_reference`) served directly in the sidecar without the bridge, and two installed-API documentation tools (`search_nuke_api_docs` / `read_nuke_api_doc`) that run in the sidecar but ask the bridge for the installed Documentation location and the API-error recovery gate. Tool profile: sidecars with `NUKE_CODEX_CONTROL_ID` (panel-managed) default to `guided` (scoped advanced `execute_python`); unmanaged external clients default to `full`; `NUKE_CODEX_TOOL_PROFILE` overrides. Guided logic: `tools/guided*.py`; manual steering: `harnesses/intervention.py` + `bridge/control.py` (pi/omp only; Linux `/proc` used to confirm retired processes). Its authenticated discovery record is `$XDG_RUNTIME_DIR/nuke-codex-panel-<uid>/session-<pid>-<hex>.json`; panes share that bridge and never stop it. User-facing detail lives in README.md only.
- Tests: smoke scripts run inside a live Nuke GUI (they `import PySide6`, which only exists in Nuke's process): `tests/chat_render_smoke.py`, `tests/chat_scroll_smoke.py` (added 8fd9ce3), `tests/*_smoke.py`, plus pytest-style `tests/test_*.py`. CI = N/A; verification is in-Nuke.
- Env: Nuke usually launched via `ghostty -e /opt/Nuke17.1v1/Nuke17.1 --nukex` from Omarchy desktop entry `~/.local/share/applications/nuke17-nukex.desktop`. Machine facts: `claude` lives ONLY at `~/.local/share/mise/shims/claude` (mise-managed; NOT in npm-global). `codex`/`pi`/`omp`/`opencode` at `~/.npm-global/bin`. MCP access to the live panel: pi `nuke` MCP server (execute_python) — requires a valid bridge discovery file.
- Pi runtime work (private install, accounts, Nuke TS extension, Pi commands in Qt, steering/cutover): read [docs/PLAN-pi-runtime.md](docs/PLAN-pi-runtime.md) first, then [docs/ARCHITECTURE-pi-runtime.md](docs/ARCHITECTURE-pi-runtime.md) and [docs/INTEGRATION-pi-runtime.md](docs/INTEGRATION-pi-runtime.md) (feature status, per-feature review workflow). Before building custom Pi behaviour (web search, `/btw`, steering, commands), check [docs/RESEARCH-pi-extensions.md](docs/RESEARCH-pi-extensions.md) and Pi 1.4.0 built-ins first. Decision log (append-only)
- 2026-10-28 CPU storm root cause + fix: panel open during ANY streaming chat pinned Nuke's main thread at 100% (node graph pan/zoom, viewer playback starve; Nuke can crash). Cause: `BubbleText.heightForWidth()` mutated `document.setTextWidth()` — layout-system width queries relayouted the document, `documentSizeChanged` → `_fit_height` → `setMinimumHeight` → layout invalidation → `heightForWidth` again: self-sustaining loop, re-kicked by every 60ms streaming render. Fix: `heightForWidth` is now a pure query returning cached `_fitted_height`; document width set only in `_fit_height` from `viewport().width()` (single width source → converges). Verified in a clean repro Nuke (no user plugins): same 8s stream stress went from 99.9% CPU + timer starvation + Nuke death → bounded CPU, returns to idle after stream, 138 bubbles 0 clipped, chat_render_smoke PASS.
- 2026-10-28 Follow-on exposed by the fix: bottom-pinning used to "work" partly because the storm kept re-emitting height_changed after the scrollbar caught up.
